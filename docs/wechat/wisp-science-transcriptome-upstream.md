# Wisp Science： 完成转录组上游分析

找到一套公开 RNA-seq 数据以后，怎样把原始测序文件变成可以用于差异表达分析的 Counts 矩阵？

这篇教程使用 Wisp Science，完成一次从样本整理、FASTQ 准备、质量检查，到基因组比对和基因计数的转录组上游分析。我们以 **GSE153250 中 MCF7 细胞的 ESR1 敲低实验**为例，只保留 siESR1 和 siNT 两组，最后得到基因 Counts、样本分组表和计数汇总。

下面保留实际使用的英文提示词，可以直接复制到 Wisp 的对话中。

## 1. 准备项目和计算服务器

在 Wisp Science 中新建一个项目，例如 `ESR1`，选择工作区，用于保存分析记录、脚本和取回的结果。模型配置可以参考 [快速开始](wisp-science-quick-start.md)。

本次上游分析在远程 Linux 服务器上执行。先按照 [服务器教程](wisp-science-servers-cli.md)，在设置中添加自己的 SSH 服务器，并确认连接可用。

服务器需要有足够的磁盘空间，容纳下载数据、解压后的 FASTQ、参考基因组和 BAM 等中间文件；STAR 比对还需要与索引规模匹配的内存。本流程不要求 GPU，CPU、内存、磁盘和网络才是主要资源。

Wisp 开始执行后，应先检查这些工具是否可用：

| 工具 | 作用 |
| --- | --- |
| SRA Toolkit：`prefetch`、`fasterq-dump` | 下载 SRA 数据并转换为 FASTQ |
| FastQC | 检查测序质量和接头等情况 |
| cutadapt | 去除接头、处理低质量末端并过滤过短 reads |
| STAR | 将 reads 比对到参考基因组 |
| samtools | 检查和处理 BAM 文件 |
| featureCounts | 根据基因注释生成计数 |

SSH 连通只说明能够访问服务器，不代表软件、参考和磁盘都已经准备好。后续命令必须使用你自己的服务器环境和实际路径。

## 2. 先弄清楚数据里有哪些样本

这次选择的数据集是 **GSE153250**。在正式下载前，我们先让 Wisp 按处理分组整理样本：

```text
What specific samples are included in GSE153250? Please organize them by treatment group.
```

数据集中包括 siNT、siESR1、siGATA3 和 siTET2 四组。我们这次只研究 ESR1 敲低相对于对照的变化，因此保留前两组：

| 分组 | 样本数 | 本次是否保留 |
| --- | --- | --- |
| siNT | 6 | 保留，作为对照 |
| siESR1 | 6 | 保留，作为 ESR1 敲低组 |
| siGATA3 | 6 | 排除 |
| siTET2 | 6 | 排除 |

如果希望先了解从原始测序数据重新处理需要多少下载量，以及要经过哪些步骤，可以继续输入：

```text
If I reanalyze the raw sequencing data, approximately how much data would I need to download, and what steps would be required for the analysis?
```

这一步要特别区分 **样本** 和 **测序 run**。本数据是单端、50 bp 测序，同一样本拆分在多个 lane/run 中。保留的 12 个样本，每个样本对应 8 个 SRR，因此需要整理 **96 个 SRR**。

96 个 run 并不意味着 96 个生物学重复。它们应按样本归并，最终 Counts 矩阵对应的是 12 个样本列。下载范围缩小到这两组后，也应重新核算磁盘需求，不能把整个数据集的下载估算直接当成本次实际用量。

## 3. 向 Wisp 提出完整的上游任务

服务器配置完成、分析范围明确以后，发送：

```text
Connect to the remote compute host, locate the FASTQ data for GSE153250, keep only the siESR1 and siNT groups, and exclude all other groups. Perform transcriptome upstream analysis to obtain the Counts data.
```

这段提示词说明了执行地点、数据集、保留分组、排除分组和最终目标。Wisp 随后检查服务器环境，定位已有 FASTQ；对于尚未准备好的数据，再根据样本与 SRR 的对应关系进行下载和整理。

在这一阶段，重点看它有没有正确保留样本。本次整理出的 GSM 如下：

| siNT | siESR1 |
| --- | --- |
| GSM4636683 | GSM4636684 |
| GSM4636687 | GSM4636688 |
| GSM4636691 | GSM4636692 |
| GSM4636695 | GSM4636696 |
| GSM4636699 | GSM4636700 |
| GSM4636703 | GSM4636704 |

表格只是并排列出两个分组，不表示同行样本构成配对。每个 GSM 对应的 SRR、处理条件和测序布局都应从元数据核实，并保存为清单，后续合并和计数都以这份映射为依据。

## 4. 下载并确认所有 FASTQ 已经准备好

本次通过 SRA Toolkit 下载和转换数据。长时间的下载任务在远程运行，过程中查看运行状态和日志，完成后逐项核对预期 SRR 与实际文件。

这次下载并非第一次就全部成功：最初 **95/96 个 SRR** 成功，缺失的是 **SRR12090795**，属于 siESR1 组的 GSM4636692。定位失败项并重试后，才补齐全部 96 个文件。

这是一个很重要的检查点。不能因为大多数文件已经下载，就默认某个样本少一个 lane 也可以继续。应先确认缺失原因，补齐后再生成该样本的最终合并 FASTQ。

下载结束至少检查以下内容：

- 预期的 SRR 是否全部存在，是否有失败或重复项。
- 文件是否非空，压缩文件是否完整，FASTQ 记录是否可解析。
- run 与 GSM、处理组的对应关系是否正确。
- 当前数据是否确实是单端测序，是否误用了双端文件处理方式。

对于下载不完整的文件，不能只根据“文件已经存在”就跳过重试。文件存在和文件可用是两件事。

## 5. 合并 lane，完成质量检查与接头处理

96 个 run 准备好以后，按同一个 GSM 的映射，将每个样本的 8 个 lane 合并为一个样本级 FASTQ，最终得到 12 个样本输入。

合并时只合并同一个样本的技术数据，不能把整个 siNT 组或 siESR1 组合成一个文件。合并全部生物学样本会丢失重复之间的信息，影响后续统计分析。

本次处理顺序是：**合并 lane → FastQC → cutadapt**。

FastQC 用于检查合并后的测序数据。查看每碱基质量、接头含量、长度分布、GC 和重复情况时，要结合 RNA-seq 数据特征判断。单个告警不能直接等同于样本不可用，例如高表达转录本本身就可能带来较高重复。

本次使用 FastQC 0.12.1 和 cutadapt 5.0，cutadapt 处理 TruSeq 接头，并设置质量阈值 20、最短保留长度 20 bp。处理后应查看日志中的 reads 保留数、接头去除和过短 reads 丢弃情况。

这些是当前数据采用的参数，不应照搬到所有实验。自己的数据需要先确认实际文库接头；对于 50 bp 短 reads，也要留意过度修剪造成的信息损失。需要评估处理后质量时，可以补充清洗后质控，与处理前报告一起检查。

## 6. 使用 STAR 比对到参考基因组

清洗后的 FASTQ 接下来进入 STAR。本次使用 **STAR 2.7.11b**，比对到 **GRCh38**，生成按坐标排序的 BAM。

开始比对前，需要核对三件事：

| 检查项 | 为什么重要 |
| --- | --- |
| 参考物种与组装版本 | 当前数据来自人类，不能误用服务器上其他物种的参考 |
| FASTA、GTF 与索引的来源 | 后续计数需要使用与比对参考匹配的基因注释 |
| STAR 与索引版本兼容性 | 已有索引不一定能被当前 STAR 直接使用 |

这次服务器上找到了 `refdata-gex-GRCh38-2024-A` 参考目录，但第一次比对仍然失败，STAR 退出码为 105。继续查看错误日志后，发现使用的 `star` 索引由 **STAR 2.7.1a** 构建，与当前 **2.7.11b** 不兼容。

参考目录中还有一个匹配版本的 `star_v11b` 索引，切换到它以后继续运行。这里定位的是本次日志明确指出的兼容性问题，不能把所有退出码 105 都直接归因于索引版本。

已经验证有效的合并、质控和修剪结果可以复用，从比对阶段恢复。若不存在可用的兼容索引，则需要评估重建索引或使用匹配版本 STAR，并记录参考与软件版本。

这次使用了服务器现有的参考包。换成完整 GENCODE 或其他注释时，纳入的基因范围和最终矩阵行数可能变化，因此必须记录具体参考来源，不能只写“使用 GRCh38”。

比对完成后，应查看各样本 STAR 的 `Log.final.out`，比较输入 reads、唯一比对、多重比对和未比对情况，并检查 BAM 是否完整可读。没有统一的百分比阈值能够替代这些检查；异常样本应结合质控、物种、参考和文库特征分析原因。

## 7. 使用 featureCounts 生成基因计数

BAM 准备好后，用 featureCounts 将比对到基因区域的 reads 归入相应基因。

本次采用 **featureCounts 2.0.6**，按 exon 区域计数，并按 `gene_id` 聚合到基因层面；链特异性设置为 **reverse-stranded**。

链特异性是这一步的关键参数。设置与文库不一致，可能明显降低分配率。自己的实验应依据建库信息或链特异性推断确定方向，不能只因本教程使用 reverse-stranded 就直接采用相同设置。

同时核对当前输入是单端还是双端，记录多重比对、重叠等计数规则。不同规则会改变计数定义，后续比较必须保持一致。

featureCounts 的输出包含基因计数与分配汇总。整理矩阵时，应去掉原始输出中的坐标、长度等注释列，保留一列基因 ID 和每个样本的计数，并把 BAM 路径准确映射为样本名。

最终要得到的是**原始基因 Counts**，而不是 TPM、FPKM 或已经做过对数转换的表达值。

## 8. 检查 Counts 是否可以交给下游分析

本次上游分析得到以下三个主要文件：

| 文件 | 用途 |
| --- | --- |
| `data/processed/GSE153250_counts_matrix.tsv` | 基因 Counts 矩阵 |
| `data/processed/GSE153250_sample_groups.txt` | 样本分组表 |
| `data/processed/GSE153250_featureCounts_summary.txt` | featureCounts 分配汇总 |

矩阵包含 **38,606 个基因、12 个样本**。第一列是 `Geneid`，后面为 `siNT_1` 至 `siNT_6`、`siESR1_1` 至 `siESR1_6`。不同参考与注释可能产生不同基因数，这个数字是本案例的结果，不是通用验收目标。

分组文件使用制表符分隔，列名是 `sample` 和 `group`。完成前，再确认：

- 矩阵样本名与分组表一一对应，排序正确，每组各 6 个样本。
- 基因 ID 没有意外重复，计数为非负整数，没有缺失值。
- 每个样本的总计数和计数分配情况合理，没有明显偏离而未解释的样本。
- 计数汇总中 Assigned 与各类 Unassigned 的情况已经检查。
- 分组、GSM、SRR、FASTQ 和 BAM 之间仍能追溯对应关系。

大型 FASTQ、BAM 和索引可以继续保留在服务器，先把 Counts、分组表、计数汇总及需要的质控报告取回本地项目。还应保留分析脚本、运行日志、软件版本和参考来源，方便定位问题和重新执行。

遇到运行中断时，可以通过 [轨迹](wisp-science-trajectory.md) 检查具体命令和报错，同时查看远程运行状态。本次下载补齐与索引修正都说明：完成上游分析需要逐步验证产物，最后一条“完成”的回答不能代替文件检查。

现在，我们已经把分散在多个测序 run 中的数据，整理成按生物学样本组织的基因 Counts。下一步就可以带着这张矩阵、样本分组和质控记录，进入 [差异表达、ORA 和 GSEA 的下游分析](wisp-science-rnaseq-downstream.md)。
